# easy-publisher

通过 `easy-publisher` 命令行工具向国内五个主流应用商店提交新版本。

## 最重要的一件事

**提交不可撤销。** 各应用商店都不提供撤销版本更新的 API。一旦 `upload` 成功，
要停止发布只能让用户登录各商店后台手动操作。

因此：
- 发版前必须先跑 `status` 确认各渠道状态。
- 不确定时先问用户，不要自己决定发版时机。
- 用户没有明确说"发版"或"上传"时，不要调用 `upload`。

## 凭据

凭据由工具自己从 `~/.easy-publisher/apps/<包名>.json`（权限 600）或环境变量
`EP_<渠道>_<参数>` 读取。**你不需要也不应该接触凭据值**：

- 不要读配置文件内容。
- 不要把凭据作为命令行参数传递（会进 shell 历史）。
- 用户要你帮忙配置凭据时，用 `channel set --value-file <文件>` 从文件读，
  或让用户自己设环境变量。

## 命令

所有命令都支持 `--json`，输出结构化结果到 stdout，日志走 stderr，可直接管道给 `jq`。

### 查状态（只读，发版前必做）

```bash
easy-publisher status --app com.example.app --json
```

关注三个字段：
- `reviewState`：`UnderReview` 表示正在审核，提交会被拒绝。
- `canSubmit`：false 表示此刻不能提交。
- `lastVersionCode`：线上版本号。**可能是 null** —— 应用在商店只有未上传 APK 的
  草稿版本时，渠道不返回版本号。这是正常情况，不是错误。

### 看已配置的应用和渠道

```bash
easy-publisher app list --json
easy-publisher channel list --app com.example.app    # 显示各参数是否已配置
```

`channel list` 只报参数名和"已配置/缺失/环境变量"，不报参数值。

### 发版

```bash
easy-publisher upload --app com.example.app --apk ./app-release.apk --desc "修复若干问题"
```

默认等待全部渠道完成并在 stderr 显示进度。常用选项：

| 选项 | 用途 |
|---|---|
| `--channel huawei,mi` | 只发指定渠道 |
| `--allow-same-version` | 版本号与线上相同时也允许提交（审核被拒后仅改素材时用）。版本号**低于**线上仍会被拒绝 |
| `--online-time "2026-01-15 10:00:00"` | 定时上线，不填则审核通过后立即发布 |
| `--timeout 300` | 单次请求超时秒数。vivo 大包可能需要调大 |

多渠道包（每个渠道一个 APK）：`--apk` 传目录，工具按文件名里的渠道标识匹配
（如 `app-HUAWEI-1.2.0.apk`）。需要先给应用加 `--multi-channel-apk`。

## 退出码

脚本和你都应该按退出码判断，而不是解析文本。

| 码 | 含义 | 该怎么办 |
|---|---|---|
| 0 | 成功 | — |
| 1 | 参数或配置错误 | 修正参数，不要重试 |
| 2 | 凭据缺失或被拒 | 让用户检查凭据配置 |
| 3 | 渠道返回业务错误 | 读 `message` 和 `code`，通常需要人处理 |
| 4 | 网络失败或超时 | **先看 `phase` 再决定**，见下节 |
| 5 | 不满足发布前置条件 | 读 `message`，可能是版本号问题或渠道在审核中 |
| 6 | 本地文件问题 | 检查 APK 路径 |
| 7 | 渠道响应无法解析 | 接口可能已变更，需要人排查 |

## 退出码 4 不能一律重试

`--json` 输出里有 `phase` 字段，这是判断能否重试的关键：

- `phase: "PreSubmission"` —— 失败发生在送审之前（取 token、查状态、上传文件、绑定草稿）。
  重试是安全的，远端最多留下一个草稿。可以适当调大 `--timeout` 后重试。
- `phase: "AtOrAfterSubmission"` —— 失败发生在送审这一步或之后。
  **不要重试。** 服务端可能已经受理了请求，只是响应在回程丢失（超时、连接重置都长这样，
  从客户端无法区分）。重试会重复送审或产生重复版本，而这不可撤销。

此时 `retryable` 一定是 `false`。正确做法是把情况报告给用户，请他登录对应商店的
开发者后台确认该版本是否已提交成功，确认没有之后再重试。

**不要因为看到"网络超时"就自动重试 upload。** 这是本工具最容易造成实际损害的操作。

**部分渠道成功时退出码也非零。** 不要因为退出码非零就断定全部失败 ——
读 `channels` 数组看每个渠道的结果。

## 上传耗时

大包上传以分钟计，可能数十分钟。不要同步等着。两种做法：

1. 用 Bash 的后台执行，把输出重定向到文件，之后读文件看结果。
2. 加 `--detach` 立即拿到 jobId。但注意 **CLI 的任务状态不跨进程保留** ——
   `job status` 只能查同一进程内的任务，所以 `--detach` 在 CLI 里用处有限，
   它主要是给 MCP server 那种长驻进程用的。

推荐做法是后台执行加轮询日志文件。

## 典型流程

用户说"帮我发个版"时：

1. 先 `app list` 确认有哪些应用，如果有多个，问用户发哪个。
2. `status --app <包名> --json` 看各渠道状态。如果有渠道在审核中，告知用户并问是否跳过该渠道。
3. 确认 APK 路径。用户没给就问，不要猜。
4. 复述一遍将要执行的操作（哪个包、什么版本、发到哪些渠道），**得到用户确认后**再执行。
5. 执行 `upload`，后台跑，轮询结果。
6. 汇报每个渠道的结果。部分失败时说清楚哪些成功了哪些没有 —— 成功的那些已经提交了，无法撤回。
7. 如果有渠道失败且 `phase` 是 `AtOrAfterSubmission`，**明确告诉用户不要重试**，
   并给出需要去哪个商店后台确认。不要自作主张重跑 upload。

## 已知限制

- **无法撤回版本。** 各商店 API 都不提供，只能登录后台手动操作。
- **OPPO 的 client_secret 仍在 URL query 上。** 已做 URL 编码，但凭据仍可能进入
  代理日志和网关审计。这是 OPPO 接口的限制，尚未查证是否支持 POST form。
- **华为和 OPPO 的 icon_url 报错**：部分应用提交时会遇到 `icon_url 不允许的文件格式`
  或 `sensitivePermissionIconUrl is necessary`。根因未定位，需要抓包。遇到时报给用户，
  建议先在商店后台网页提交一次补全素材。
- **渠道逻辑未经真实验证。** 本工具是从上游项目重构而来，五个渠道的提交路径
  编译通过、单元测试通过，但**没有用真实凭据向商店实际提交过**。首次使用时
  建议只发一个渠道试。
